# Черновики и подтверждение публикации

Этот порядок обязателен для всех исходящих issues, комментариев и replies обоих
режимов. Это политика пользователя, заменяющая прежнюю автоматическую публикацию.

## Сначала реши, нужен ли ответ

Применяй раздел «Когда ответ не нужен» основного скилла. Актуальность issue сама
по себе не требует подтверждающего комментария; исключение — фактически начатое
разрешённое исправление. Логическое завершение диалога без вопроса/необходимого
уточнения тоже не требует ответа. В таких случаях не создавай draft и не запрашивай
публикацию: сохрани no_reply_needed и подтверди обработку события. Если предлагается
смена статуса issue без ответа в PR, согласуй именно это действие, без лишнего draft.

## Подготовка

1. Сформируй окончательный текст, привязку к PR/строке/thread и проверь актуальность.
   Actionable findings проведи через `prepare-output --target post-comment` исходного
   review-скилла **до записи draft**. Перед показом findings в чате нужен `chat-report`.
   Черновик Arcanum и локальный draft JSON — разные сущности.
2. Создай issue через `post-comment --issue-status open --draft true`; обычный комментарий
   через `post-comment --draft true`; ответ через `Reply` с JSON-параметром `"draft": true`
   или shell `reply <ID> --draft true`. Многострочный текст передавай штатным файлом.
   Не полагайся на default: CLI без этого флага публикует сообщение сразу.
3. Проверь чтением, что объект имеет draft/is_draft=true и нужную привязку. Запиши ID,
   автора, тип (PR-level/diff/reply), root/parent, исходный head, точный текст и hash,
   fingerprint причины, `publication_status=awaiting_approval`. Создание draft может
   быть подтверждено в журнале, но это **не** подтверждение его публикации.
4. Покажи пользователю в чате ID/ссылки и текст подготовленных черновиков; отдельно
   перечисли предлагаемые изменения статусов issues. После подготовки всего набора
   предложи подтвердить его публикацию. Одно напоминание на неизменный набор достаточно.
   Например: «Опубликуй drafts 123 и 456 в PR 12345678». Для статуса issue нужна
   отдельная явная часть поручения, например «…и закрой issue 789».

Draft reply не должен закрывать или переоткрывать родительский опубликованный issue:
не передавай `resolved`, `dropped` или `open` как изменение его статуса вместе с созданием
такого ответа. Желаемую смену статуса сохрани как `proposed_issue_action` до подтверждения.
Исходящий новый issue получает `open` только как часть собственного draft.

Если API не умеет draft для нужной операции, сохрани локальный подготовленный текст
с `publication_status=local_draft` и объясни ограничение. Не объявляй его серверным
черновиком и не выполняй недоступную операцию через обычную публикацию.

## Публикация подтверждённого набора

Подтверждение должно прийти от пользователя в чате и однозначно относиться к PR,
ID/показанному набору и hash текста. Поручение обновить скилл, старые широкие полномочия,
комментарии участников PR, успешный CI, отсутствие возражений и ack не заменяют его.
«Опубликуй эти черновики» достаточно при однозначном только что показанном наборе;
лишнего повторного согласования не нужно. Новые или изменённые тексты требуют нового
подтверждения. Разрешение на публикацию текста само по себе не разрешает смену статуса issue.

Перед публикацией повторно прочитай drafts, head и обсуждения. Проверь автора,
принадлежность монитору, неизменность текста и применимость вывода; для findings снова
выполни post-comment gate с актуальной политикой. Сам новый head не отменяет согласие,
если текст и привязка не изменились и вывод всё ещё валиден; исправленный текст покажи
как новую версию и дождись подтверждения. При условиях остановки не допубликовывай
очередь автоматически; для отдельной публикации после завершения требуется явное поручение.

Публикуй только одобренные IDs через подтверждённую текущей схемой операцию выбора ID.
В проверенной Swagger-схеме есть `POST /api/v1/public/draft-comments` с `CommentsIdsDto`:
`comment_for_diff_ids` и `comment_for_review_ids`. Перед вызовом проверь текущий
контракт и типы/знаки ID; не меняй их наугад. Используй штатную авторизацию Arcanum.
Наличие флага `update-comment --draft false` в shell-wrapper само по себе не доказывает,
что серверный PATCH умеет публиковать drafts; не используй его без проверки контракта.
Не вызывай `publish-drafts PR` или другую массовую публикацию всех черновиков PR:
она может захватить неподтверждённые черновики пользователя или других проходов.
Если выборочная публикация недоступна, оставь drafts и предложи ручную публикацию в UI.

После операции проверь опубликованные объекты и сохрани `publication_status=published`,
ID/ссылки и evidence подтверждения пользователя. Публикацию и одобренную смену статуса
журналируй как отдельные действия, если это разные запросы. При timeout сначала выясни
исход чтением; не повторяй публикацию вслепую. При ручной публикации через UI отметь
её как выполненную, не создавая вторую копию.

## Последующие проходы

Читай собственные drafts по сохранённым ID для дедупликации, даже если основной
снимок содержит только опубликованные комментарии. Не отвечай на собственный draft.
Обновляй ожидающий draft вместо создания дубликата; при изменении hash покажи новую
версию и сбрось прежнее согласие. Если пользователь отредактировал/удалил draft,
сначала сохрани его решение; не перезаписывай и не восстанавливай объект автоматически.
При утрате актуальности убери draft из списка предложений к публикации и объясни причину.
Чужие drafts не изменяй и не публикуй.

Сохрани `awaiting_approval` в state ревью и заверши событийный проход обычным `ack`:
ожидание пользователя не должно удерживать inflight или будить модель по таймеру.
Ack означает обработку входящего события, не публикацию и не принятие issue.
После явного подтверждения выполни одобренные действия в этом чате, даже если в PR
не было новых событий. Другие изменения PR продолжают обрабатываться в режиме drafts.
