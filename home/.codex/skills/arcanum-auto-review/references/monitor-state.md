# Состояние и повторные запуски

Читай перед первым проходом и при восстановлении после прерывания. Это контракт
хранения, а не описание полей Arcanum API: реальные поля сверяй с ответами API/CLI.

## Размещение и владение

Храни данные в `${CODEX_HOME:-$HOME/.codex}/state/arcanum-auto-review/<pr-id>/`.
Если этот каталог недоступен, используй разрешённый постоянный каталог рабочего
пространства вне checkout и зафиксируй абсолютный путь в конфигурации скриптового планировщика.
Не используй `/tmp` для единственной копии состояния. Не коммить это состояние
в репозиторий. Не сохраняй секреты и полные логи с потенциальными credentials.

Один PR обслуживает один владелец: poller registration (PR ID) + chat ID + host. Перед созданием
расписания сверяй и этот файл, и существующие автоматизации по PR/skill. Не создавай
второго писателя из другого чата; сообщи о действующем мониторе. При утрате локального
состояния сначала восстанови сведения из обсуждений, remote history и автоматизации.

На время прохода атомарно создай каталог `run.lock` (mkdir без exist_ok) и запиши
run ID, владельца, host и время. Если lock уже есть, этот проход не пишет в PR.
Не снимай чужую блокировку только из-за возраста: длительный анализ может быть жив.
Осиротевшую блокировку восстанавливай лишь после подтверждения завершения её владельца;
если проверить нельзя — сообщи о блокировке и не запускай второго писателя.
Освобождай только свою блокировку в finally, включая ошибки и закрытие PR.

`state.json` обновляй записью временного файла в том же каталоге и атомарным rename.
Если файл повреждён, сохрани его и восстанови состояние; не сбрасывай молча в пустое.

## Какие сведения сохранять

- `schema_version`, PR ID/URL, remote branch, владелец, poller PR ID (и прежний automation ID при миграции), absolute paths.
- Стабильный ID автора PR и снимок его текущего голоса ревью; при остановке по ship —
  подтверждённый голос, его автор и время наблюдения.
- Разрешённые операции и ссылка/текст исходного поручения; ограничения пользователя.
- `observed_head`, active diff/base, **отдельно** `reviewed_head`: продвигай последний
  только после завершения всего анализа выбранной ревизии и регистрации всех findings.
- Снимок опубликованных комментариев/replies: ID, parent/thread ID, author ID,
  SHA-256 текста, статус issue, anchor, ревизия, результат обработки этой версии.
- Issues: последний рассмотренный head, статус валидности, доказательства/решение,
  fingerprint корневой причины и ID существующей ветки обсуждения.
- Checks: стабильный check ID/name, проверяемая ревизия, run/attempt ID, статус,
  fingerprint ошибки и результат диагностики. Время опроса не является новым событием.
- Политики и требования: ревизия и hashes использованных документов/описания задачи.
- `pending_events`, `actions`, собственные comment/commit IDs, ожидаемые новые CI runs,
  пути сохранённых patches, последний отправленный пользователю blocker.

Обновление timestamps без изменения смысла не требует нового ответа. Не полагайся
только на updated_at: статус issue, текст и CI attempt могут изменяться независимо.
Если CLI не возвращает replies/author IDs/пагинацию, дополни снимок доступным штатным
API. Если полный снимок не получить, отметь источник неполным и сохрани старую очередь;
не заявляй «изменений нет» и не делай публикации, для которых невозможна дедупликация.

## Ключи событий и действий

Используй стабильные сериализованные поля и SHA-256, а не встроенный `hash()`:

- commit review: PR + active diff/base + head;
- `/ask`: PR + comment ID + hash текста (при правке вопроса получается новая версия);
- issue assessment: PR + issue ID + hash текста/статуса + рассматриваемый head;
- CI diagnosis: PR + check ID + commit + run/attempt + статус/failure fingerprint.

Ключ внешнего действия должен отражать **намерение**, а не один опрос. Для finding
используй PR + путь/символ + корневую причину + сценарий, не только строку или head.
Так перенос строк и новый commit не создают дубликат старого issue. Помимо ключа
сравнивай существующие обсуждения семантически, в том числе опубликованные человеком.
Для ответа используй event key + родительский comment ID; для fix — причина + input head.

## Журнал побочных эффектов

Перед внешним действием атомарно сохрани запись `prepared`: action key, тип, исходный
head, целевой объект/ветку, hash и точный payload после gate, ожидаемый результат.
Статусы доставки: `prepared`, `confirmed`, `uncertain`, `waiting`, `failed`.
Подтверждённое создание draft не означает согласие на его публикацию.

После успеха проверь удалённый объект и сохрани `confirmed` с comment ID или commit SHA.
Если timeout/обрыв случился после запроса, поставь `uncertain` и **не повторяй запись**
вслепую. Повторно прочитай комментарии нужной ветки или remote commits; сопоставь
автора, parent, точный payload/commit и время. Если найден результат — подтверди его;
если достоверно установлено отсутствие — можно повторить действие. Если исход
неопределён, оставь ожидание и сообщи о нём; не считай неопределённость отсутствием.

Для push сохраняй отдельно commit SHA, parent, целевую ветку и результат публикации.
Если commit уже в remote, восстанавливай только недостающий комментарий. Новый remote
head может быть потомком этого commit — это не означает, что push не состоялся.
Перед повторным commit проверь журнал и историю; не создавай тот же fix второй раз.

Получение события и его обработка — разные отметки. Продвигай снимок наблюдений,
сохраняя необработанные события отдельно. Сбой одного события не теряет остальные.
При отсутствии новых событий всё равно проверь `pending_events`, неопределённые
действия и ожидаемый CI, но не повторяй подтверждённые ответы.

Повторяющийся blocker уведомляй один раз до существенного изменения. Для временной
ошибки чтения оставь работу следующему 10-минутному проходу; не крути быстрый retry-loop.
При недостающей авторизации или необходимости решения человека останови зависимые
записи до устранения причины. Успех fetch не означает успех анализа/публикации.

## Завершение

При merged/closed, ship от автора PR или просьбе остановить: останови именно сохранённую
автоматизацию через инструмент и проверь результат, запиши terminal status и причину
остановки. Прекрати обработку очереди, повторные публикации и push, включая восстановление
незавершённых действий. Снятие ship или новый head не возобновляют завершённый мониторинг:
для возобновления нужно новое поручение пользователя. Сохрани непушенные
patches и журнал; убирай только собственный mount после проверки отсутствия ценных
изменений. Если расписание остановить не удалось, локальный terminal status должен
делать следующие проходы бездействующими, кроме повторной попытки остановки и
однократного уведомления о сбое.

## Граница скрипта и агента

Скрипт хранит отдельные `poll-state.json`, `latest-snapshot.json` и неизменяемые
`events/<ID>.json` в `~/.local/share/arcanum-pr-poller/<PR>/`. Не смешивай его
baseline с `fully_reviewed`/`reviewed_head` в state ревью. Подтверждение ack означает
завершение доставки одного события, а не отсутствие ошибок в коде или закрытие issues.
Работу, заблокированную отсутствующими данными, сохрани в state ревью и ack blocked;
она не вызывает новые проходы на неизменном PR. Новые ответы/commits/CI снова пробудят
агента. После собственных комментариев возможен один дополнительный проход по их
изменению; журнал review не позволяет повторить запись.

## Drafts, approval и миграция полномочий

Для каждого исходящего текста храни `publication_status` (`local_draft`,
`awaiting_approval`, `approved`, `published`, `superseded` или `cancelled`), draft ID,
PR/root/parent, draft/is_draft, автора, точный content/hash, исходный head и
`proposed_issue_action` при предложении сменить статус. Для согласия сохраняй
сообщение пользователя, одобренные IDs и hashes; обновление текста отменяет согласие.
Стадии доставки draft и его публикации — отдельные записи журнала.

Старые permissions на прямую публикацию/resolve и prepared/pending действия не
разрешают завершить их без нового согласия. На первом проходе по обновлённому скиллу
отметь draft-first publication policy в state; неподтверждённые исходящие действия
переведи в ожидание согласия. Уже опубликованные объекты не удаляй и не меняй.
При unknown outcome сначала узнай фактический результат; запрет повторной
публикации без согласия действует и при восстановлении после обрыва.

Собственные drafts сверяй с сервером по ID и считай подготовленным результатом
анализа, а не опубликованным ответом. Не используй только список опубликованных
комментариев для дедупликации. Ожидание согласия сохраняется после обычного ack
и не запускает модель повторно. Выполнение publish/resolve/reopen возможно лишь
после проверки approval из [draft-publication.md](draft-publication.md).
