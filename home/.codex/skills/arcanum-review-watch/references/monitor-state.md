# Состояние монитора чужого PR

Это локальный контракт хранения, а не схема Arcanum API. Реальные поля сверяй
с текущим ответом API/CLI; недостающие replies и пагинацию получай штатным источником.

## Хранение, владение и блокировка

Каталог: `${CODEX_HOME:-$HOME/.codex}/state/arcanum-review-watch/<pr-id>/`.
При отсутствии доступа используй постоянный разрешённый каталог вне checkout,
сохрани абсолютный путь в конфигурации скриптового планировщика. `/tmp` не годится для единственной копии состояния.
Не сохраняй токены, секреты или полные потенциально чувствительные логи.

Один монитор на PR: poller registration (PR ID) + chat ID + host. При включении проверь существующие
автоматизации и состояния `arcanum-review-watch` и `arcanum-auto-review`. При уже
действующем другом мониторе сообщи о нём вместо создания дубликата. Чтение исходного
скилла не переносит его полномочия на этот монитор.

На проход атомарно создай `run.lock` через mkdir без exist_ok, сохрани run ID,
владельца, host и время. Если блокировка занята, пропусти проход. Снимай лишь свою
блокировку в finally. Возраст не доказывает, что чужой проход умер: восстанавливай
осиротевший lock только после подтверждения завершения владельца. При неопределённости
сообщи о препятствии вместо одновременных записей.

Сохраняй `state.json` атомарно через временный файл в том же каталоге и rename.
Повреждённое состояние не сбрасывай молча: сохрани исходник и восстанови по удалённым
данным. Сведения о чужом авторстве не угадывай.

## Поля состояния

- schema version, PR ID/URL, poller PR ID, chat/host IDs, прежний automation ID при миграции, абсолютные пути, полномочия;
- стабильный ID автора PR и снимок его текущего голоса ревью; при остановке по ship —
  подтверждённый голос, ID голосующего и время наблюдения;
- observed head/base/diff и **отдельно** fully reviewed head/base/diff, fingerprints
  требований/политик, покрытые файлы и пробелы анализа;
- comments/replies: ID, root issue/thread ID, parent ID, author ID, hash текста,
  draft/status, anchor/revision, обработанная версия;
- `owned_issues`: root comment ID, доказательство создания этим монитором, author ID,
  fingerprint причины, исходный finding, опубликованный payload, статус, история
  оценок valid/fixed/obsolete/invalid/needs-evidence, доказательства и проверенный head;
- все replies собственных issues, в том числе закрытых, и версия каждого ответа;
- CI: check ID/name, commit, run/attempt ID, status, fingerprint ошибки и диагностика;
- очередь pending events, actions journal, ожидаемые данные/CI, последний blocker.

Не определяй владение только по login. Подтверждённый ID, полученный после создания,
и прочитанный author должны согласоваться. Исторические issues того же аккаунта не
добавляй в owned_issues без доказательства происхождения или поручения пользователя.

## Дельта и дедупликация

Используй стабильные поля и SHA-256, не process-dependent `hash()`:

- review event: PR + head/base/active diff + fingerprints требований/политик;
- reply event: PR + root issue ID + reply ID + hash текста/status;
- issue recheck: PR + owned issue ID + head + hash обсуждения/status;
- ask event: PR + comment ID + hash текста;
- CI event: PR + commit + check + run/attempt + status/failure fingerprint.

Скачивай все страницы и полные деревья обсуждений. Изменение timestamp без нового
содержимого не событие. Если снимок неполон, сохрани старые данные и очередь; нельзя
объявлять «нового нет» или закрывать issue на основании отсутствия reply в обрезанном
ответе. Новый head требует перепроверки своих открытых issues даже без replies.

Дедупликация finding: PR + путь/символ + корневая причина + сценарий, не только
head/строка. Сравнивай также по смыслу с чужими и снятыми issues. Разные event keys
могут относиться к одному действию: новый commit и ответ «исправил» не требуют двух
закрывающих ответов. Несколько replies можно покрыть одним ответом с перечнем
обработанных event IDs. Отмечай их выполненными лишь после подтверждённого действия.

## Журнал и восстановление

До внешней записи сохрани `prepared`: action key, PR/head, root/parent comment ID,
тип действия (create/reply/resolve/reopen), ожидаемый статус, точный проверенный payload
и hash. После записи прочитай объект и отметь `confirmed` с ID/ссылкой.

При timeout/обрыве сохраняй `uncertain`, не повторяй запись вслепую. Перечитай нужную
ветку, сопоставь автора/parent/точный payload и итоговый status. Подтверди найденный
результат; повторяй лишь после достоверного установления отсутствия. Если исход
неизвестен, оставь в очереди и сообщи о препятствии. У одного закрытия могут быть
две записи: ответ-обоснование и изменение статуса. Успешный ответ не повторяется,
если не удалась лишь смена статуса; перед её повтором снова проверь head и обсуждение.

Observed snapshot и выполненная работа различаются. Продвигай reviewed revision
только после полного анализа всех файлов/требований выбранного diff и регистрации
результатов; публикации могут оставаться в явной очереди. Не продвигай её при
недоступном коде/политике. Сбой одного события не стирает остальные.

При следующем проходе обрабатывай pending/uncertain даже без новых событий. Не
повторяй подтверждённые ответы, закрытия или одинаковые уведомления о blocker.
Временный сбой чтения отложи до следующего 15-минутного запуска; не крути retry-loop.
Недостаток данных не превращай в доказательство невалидности собственного issue.

## Завершение

При закрытии/слиянии PR, ship от автора PR или остановке пользователем прекрати комментарии и смены
статусов, останови PR через `poller.py stop --pr <ID>` (или `ack --stop`) и проверь status.
Прекрати обработку очереди и повторные записи, включая восстановление незавершённых
действий. Запиши terminal state и причину остановки, сохрани журнал и убери только
собственный временный mount. Снятие ship или новый head не возобновляют завершённый
мониторинг: для возобновления нужно новое поручение пользователя.
Если остановка расписания не удалась, terminal state запрещает последующим проходам
писать в PR: они могут лишь повторить остановку и один раз сообщить о сбое.

## Граница скрипта и агента

Скрипт хранит отдельные `poll-state.json`, `latest-snapshot.json` и неизменяемые
`events/<ID>.json` в `~/.local/share/arcanum-pr-poller/<PR>/`. Не смешивай его
baseline с `fully_reviewed`/`reviewed_head` в state ревью. Подтверждение ack означает
завершение доставки одного события, а не отсутствие ошибок в коде или закрытие issues.
Работу, заблокированную отсутствующими данными, сохрани в state ревью и ack blocked;
она не вызывает новые проходы на неизменном PR. Новые ответы/commits/CI снова пробудят
агента. После собственных комментариев возможен один дополнительный проход по их
изменению; журнал review не позволяет повторить запись.
