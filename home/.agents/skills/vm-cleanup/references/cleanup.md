# Команды и восстановление

Команды выполняются на установленной целевой Linux VM после диагностики и в пределах разрешённого плана из SKILL.md. Пороги из вики — исходные примеры, а не обязательная политика хранения.

## Кеш ya и uservices

Проверь потребителей кеша: текущие сборки, тестовые окружения и IDE. Не останавливай их без разрешения. Уточни поддерживаемые параметры установленного `ya` через справку, если версия отличается.

```bash
ya gc cache --age-limit=0
```

Это агрессивная очистка кеша ya: последующие сборки могут заново загружать или создавать артефакты. Не заменяй её удалением всей `~/.ya`.

`make clean` из статьи относится к конкретному проекту uservices. Найди действительный корень проекта и прочитай цель `clean`, включаемые Makefile и вызываемые скрипты. Она может выполнять `arc clean -Xd`, удалять игнорируемые файлы, каталоги сборки и останавливать testsuite. Сначала проверь, нет ли среди них нужных локальных данных. Не запускай `make -n` как гарантированно безопасную инспекцию: Makefile может выполнять команды даже при разборе. Если поведение неясно или противоречит запрету запускать тестовые обёртки, пропусти цель до уточнения. Не копируй пути и логин автора из вывода вики.

## Journald

Диагностика:

```bash
sudo journalctl --disk-usage
du -sh /var/log/journal /run/log/journal
```

После выбора объёма и срока сохраняемой истории можно использовать пример из статьи — 100M и 2 дня:

```bash
sudo journalctl --rotate
sudo journalctl --vacuum-size=100M --vacuum-time=2d
sudo journalctl --disk-usage
```

Vacuum удаляет архивные файлы, а disk-usage учитывает и активные. Ротация делает прежние активные файлы доступными для vacuum. При совместном указании ограничений удаление идёт до выполнения обоих; два дня не гарантируют сохранение двух дней истории при лимите 100M. Не обещай точные 100M итогового расхода.

Для постоянного ограничения после разрешения на изменение конфигурации проверь основной конфиг и drop-in файлы. Подготовь отдельный drop-in в `/etc/systemd/journald.conf.d/`, не перезаписывая существующий файл. Для логов на диске пример такой:

```ini
[Journal]
SystemMaxUse=100M
```

`SystemMaxUse` относится к `/var/log/journal`; `RuntimeMaxUse` — к `/run/log/journal`. Статья предлагает RuntimeMaxUse для проблемы в `/var/log/journal`; здесь это исправлено. Сохрани прежний конфиг, примени изменение штатным перезапуском `systemd-journald.service` только в разрешённом объёме и проверь состояние службы и расход диска. Откат конфигурации не возвращает удалённые логи.

Если vacuum не помог, проверь активные файлы, journal namespaces, ошибки чтения и открытые удалённые файлы. Не используй приведённое в вики массовое `find ... | xargs rm` для всех журналов. Повреждённые журналы требуют отдельного точечного разбора.

Уточнения проверены по документации [journald.conf](https://www.freedesktop.org/software/systemd/man/252/journald.conf.html) и [journalctl](https://www.freedesktop.org/software/systemd/man/255/journalctl.html); при выполнении учитывай локальную версию systemd.

## Старые файлы в /tmp

Сначала выведи только кандидатов верхнего уровня, без обхода их содержимого и без раскрытия glob оболочкой:

```bash
find /tmp -xdev -mindepth 1 -maxdepth 1 \( -type f -o -type d \) \( -name 'core-*' -o -name 'vscode-ssh*' \) -mtime +3 -ls
```

Проверь каждого кандидата: владелец, реальный путь, размер, активные VS Code/SSH-сессии и процессы, использующие его. Каталоги исследуй отдельно, исключая вложенные маунты: внутри могут быть свежие файлы. Если нельзя подтвердить, что кандидат не используется, пропусти его. Core dumps могут быть нужны для отладки — учитывай задачу пользователя.

После разрешения удаляй точный проверенный список с корректным quoting и `--`; при передаче списка между командами используй NUL-разделение. Не удаляй весь `/tmp` и не повторяй рекурсивный `find ... -exec rm -rf` из статьи без отбора. GNU `-mtime +3` использует полные суточные интервалы, а не точную границу 72 часа.

## Preamble clangd

Сначала проверь, какие процессы clangd работают и кому принадлежат файлы. Сформируй список:

```bash
find /place/vartmp -xdev -type f -name 'preamble-*.pch' -mtime +15 -ls
```

Начни без sudo; при нехватке прав не считай выборку полной. При необходимости и наличии разрешения повтори с sudo. Шаблон намеренно не включает `.pch.tmp`: статья не обосновывает очистку активных временных файлов.

После проверки возраста, владельцев и отсутствия использования удаляй только перечисленные файлы. Не расширяй шаблон до `preamble*`. Для стабильной проверенной области команда из вики с дополнительными ограничениями имеет вид:

```bash
find /place/vartmp -xdev -type f -name 'preamble-*.pch' -mtime +15 -delete
```

Применяй её только если вся повторная выборка входит в разрешённый план; иначе используй точный список. Сам по себе возраст не доказывает, что файл никем не используется.

## Arc: кеш объектов

Выполни `arc mount --list` и сопоставь нужный mount с его store и object_store. Измеряй эти физические пути, а не виртуальное дерево Arcadia. Из целевого исправного маунта запиши `arc status`, изменения staged/unstaged и состояние локально изменённых и неотслеживаемых файлов; для значимых файлов сохрани контрольные суммы.

```bash
arc gc --dry-run
```

После проверки оценки и разрешения на этот GC выполни один `arc gc`. Уже данное разрешение не запрашивай повторно. Затем повтори `arc status`, `arc diff`, `arc diff --cached` и проверь записанные файлы/контрольные суммы.

GC предназначен для object cache. Не обещай очистку traces или уменьшение RocksDB/overlay: большие такие каталоги требуют отдельной диагностики. Если доступен скилл `arc`, используй его актуальный раздел mount/storage hygiene; отсутствие этого скилла не разрешает вручную удалять внутренности store.

## Arc: Transport endpoint is not connected

Ошибка getcwd означает, что текущий путь недоступен; она сама по себе не доказывает удаление кода или единственную причину сбоя. Перейди в заведомо доступный физический каталог, например `/`, и проверь `arc mount --list`, таблицу маунтов, свободное место и процессы Arc/IDE.

Определи исходные mount, store и object_store. Восстанавливай прежнюю конфигурацию, не создавай произвольное новое хранилище. В статье `arc mount arcadia` выполняется относительно домашнего каталога; используй фактический абсолютный путь и справку установленного Arc. Не выполняй принудительное unmount или kill вслепую.

Если точка монтирования непуста:

1. Убедись, что это действительно обычный каталог без активного/зависшего маунта и вложенных маунтов. Если состояние неоднозначно, останови восстановление и выясни его.
2. Проверь файлы: IDE могла записать изменения после потери маунта. Согласуй остановку записи, если она ещё продолжается.
3. Сохрани каталог переименованием в уникальный соседний путь на том же разделе, например `arcadia_save-<timestamp>`. Не перезаписывай существующий backup. Это сохраняет данные, но не освобождает место.
4. Восстанови исходный Arc-маунт с прежним store. Сравни сохранённые файлы с рабочим деревом, верни нужные изменения выборочно без слепой перезаписи; проверь статус и содержимое.
5. Оставь backup до подтверждения сохранности работы; затем вернись к диагностике расхода места.

Вики упоминает удаление рабочей папки Arc как крайний способ и предупреждает о потере локальных веток и стэшей. Не включай его в обычную очистку: одного сохранённого токена недостаточно для сохранения пользовательской работы.
